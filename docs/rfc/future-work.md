# 未来工作

> 状态：**提案** · 负责人：跨切面 · 依赖：完整的 v2 RFC 集（T2-T6）和 `docs/rfc/_architecture-decisions.md`（T1）。
> 范围：本文件列举 v2 RFC 显式作为 Non-Goal 推迟的每一个条目，并为每一条陈述：证明重新纳入合理的**触发条件**、**粗略工作量**，以及对已发布或未来 RFC 的**前置依赖**。这是一份规划文档，不是承诺。本文件不修改 `apps/` 或 `packages/` 下的任何源码。

## 动机

v2 RFC 集（T2 至 T6）做了有意的范围裁剪。每份 RFC 都带有一个 Non-Goals 章节，点名它拒绝规范的内容，并且 `_architecture-decisions.md` 中的若干决策（A1-A5、B6、B7）明确把条目推迟到"未来的 RFC"。这些推迟散落在六份文档中；一个想要知道"我们什么时候能有 marketplace？"或"多 Agent 编排什么时候提上日程？"的实现者或下游规划者，必须阅读全部六个 Non-Goals 章节并交叉引用这些决策。

本文件把每个推迟条目汇聚到一份清单中，并且 —— 关键地 —— 为每个条目附上一个具体的**触发条件**。触发条件是使条目值得启动的可观察信号（协议稳定、用户需求、某个依赖落地）。没有触发条件，待办列表就变成愿望清单；有了它们，它就变成一份对真实信号而非热情做出反应的、有顺序的计划。

## 目标

- 在一处**枚举** T2-T6 的**全部** Non-Goal 条目以及决策 B6/B7，使被推迟的内容不被遗忘。
- 为每个条目附上**触发条件**（证明启动合理的可观察信号）、**粗略工作量估算**（小型 / 中型 / 大型 / 超大型），以及对已发布或未来 RFC 的**前置依赖**列表。
- 让本文件保持**诚实**：触发条件是"商业决策待定"或"需要独立 RFC"的条目就这样标注，而不是伪装成工程任务。

## 非目标

- **承诺日期。** 触发条件是信号，不是时间表。本文件中没有任何条目有日历日期。
- **重新规范被推迟的条目。** 每个条目指向其源 RFC 中权威的 Non-Goal 陈述；本文件只添加触发条件、工作量和依赖元数据。
- **重开 v2 决策。** 如果某个条目因为某个陈述过的理由被裁掉（例如 B7 裁掉完整 Artifact 子系统以避免 RFC 膨胀），本文件尊重那个理由。重新纳入通过一份新 RFC 进行，而不是通过修订这份规划说明。
- **覆盖实现 bug 或打磨工作。** 这是新子系统的战略路线图，不是 bug 跟踪器。

## 规范

下面每个条目都遵循同一结构：一段简短描述、证明启动合理的触发条件、粗略工作量、前置依赖，以及对源 Non-Goal 或决策的交叉引用。

### 1. 插件 Marketplace / Registry

**描述。** 一个中心化或联邦化的 registry，用户在其中浏览、搜索、安装和评价插件。用可发现的模型取代当前的"在磁盘上放一个目录"分发模型。

**触发条件。** 插件协议（T4 清单、T5 扩展点和 T6 安全）已经实现稳定至少一个 minor 发布周期且没有 schema 破坏性变更，**并且**存在可衡量的用户需求（一群插件作者在项目之外发布插件，或反复出现对发现界面的请求）。

**前置依赖。** T4 清单 schema 冻结。T5 扩展点接通。T6 权限上限和沙箱强制执行，使 marketplace 不至于变成攻击面。一份签名交付 RFC（下面的条目 2）应先落地或与之同步。

**粗略工作量。** 超大型。一个 marketplace 是一项服务（托管、搜索、评分）、一个客户端（浏览 + 安装 UX）和一套策略（策展、下架、评分滥用）。每一项都是多周的工作流。

**来源。** T4 Non-Goals；T6 Non-Goals。

### 2. 插件签名 / 供应链安全

**描述。** 一套针对插件包的代码签名方案：对 `plugin.json` 加包摘要的可验证签名、密钥分发与轮换机制，以及针对被攻陷插件的撤销通道。

**触发条件。** 这**必须**（MUST）在 marketplace 上线**之前**落地。没有签名，marketplace 就是一个未缓解的供应链攻击面（篡改、typosquatting、被弃包攻陷 —— 全部在 T6 §8 中枚举）。因此触发条件是"marketplace 决策已作出" —— marketplace 一上路线图，这个条目就成为阻塞项。

**前置依赖。** T6 威胁模型（已作为 RFC 发布），它固定了签名方案必须满足的策略：Tier 2 插件**必须**（MUST）呈现可验证的签名；未签名插件**必须**（MUST）被当作 Tier 3；`source` 字段在校验之后由 host 控制，而非作者自填。签名算法（Ed25519 over a detached SIG 文件是领先候选）、密钥分发和撤销是实现工作。

**粗略工作量。** 大型。密码学是容易的部分；密钥分发、轮换和撤销是困难的部分，需要运营基础设施。

**来源。** T6 Non-Goals（"实现代码签名、签名校验或密钥基础设施"）；T6 §8（供应链威胁）。

### 3. 多 Agent 编排

**描述。** 在单一会话内或跨会话以协调拓扑运行多个 Agent 的能力 —— 一个 swarm、一个 subagent fan-out，或一个 supervisor-worker 模式。

**触发条件。** 单 loop + mode hint 模型（决策 B6）无法服务的明确用户场景。当前 v2 loop 能很好地处理每会话一个 Agent；只有当真实工作流明显需要并行 Agents、专家路由或跨会话交接时，编排才合理。投机性的"我们可能需要 swarm"不是触发条件。

**前置依赖。** T2 Agent Loop v2（Run 生命周期、并发工具池和 stop_reason 路由）必须实现完备，因为编排层组合 Runs。自定义 Agent preset（2026-06-20 计划的 Phase 3）也应已落地，以便编排组合的是真实的 Agents，而不仅是隐式的默认 Agent。

**粗略工作量。** 超大型。编排引入新的拓扑层、Agent 间消息传递和协调运行时。它本身至少是一份 RFC，可能本身就是一个 RFC 系列。

**来源。** T2 Non-Goals（"多 agent / swarm / subagent 图"）；决策 B6（选了单 loop + mode hint 而非编排）。

### 4. Computer Use

**描述。** 集成 Anthropic 的 Computer Use 能力（或等价物），允许 Agent 通过 screenshot-and-action 循环驱动桌面、浏览器或图形环境。

**触发条件。** Anthropic Computer Use API 已稳定并文档化为生产可用（不是 beta），**并且**存在明确的用户对 MyCopilot 桌面自动化的需求。稳定性很重要，因为 beta API 会在每次破坏性变更时被迫重新实现。

**前置依赖。** T2 Agent Loop v2（Run 生命周期和 stop_reason 路由必须处理长时间运行、多步工具序列）。工具安全模型（`docs/2026-07-11-tool-safety-system-design.md`）必须把 Computer Use 动作分类为 `danger` —— 每个屏幕动作都是副作用 —— 因此每次调用的确认路径会被频繁行使。

**粗略工作量。** 大型。一个 Computer Use 集成是一个新的工具家族、一个 screenshot/action 流式界面，以及针对确认疲劳（因为每个动作都是 `danger` 级）的大量 UX 工作。

**来源。** T2 Non-Goals（"Computer Use、Voice 或后台守护进程"）。

### 5. 语音 / 多模态输入输出

**描述。** 语音输入（speech-to-text）、语音输出（text-to-speech），以及多模态输出（图像生成、超出 Artifact Renderer 协议的结构化数据可视化）。

**触发条件。** 每个模态都有**自己独立的 RFC**；不存在统一的"多模态"触发条件。语音输入在免提使用成为可衡量用例时合理。图像输出在某供应商的图像生成 API 稳定且用户请求它时合理。每个模态的触发条件是"用户需求 + 供应商 API 稳定性"，按模态分别评估。

**前置依赖。** T2 的 Extended Thinking 暴露（`delta` 上可选的 `kind` 字段）示范了叠加 SSE 字段的模式；语音/多模态会遵循同样的"扩展，不重定义"方法。T3 的附件增强（PDF、图像、音频输入）是已规范的输入侧前置依赖。输出侧多模态除 T2 外目前没有前置依赖。

**粗略工作量。** 每个模态中型。每个模态是一个新适配器、一个新的 SSE 字段族（叠加）和前端渲染工作。

**来源。** T2 Non-Goals（"Computer Use、Voice 或后台守护进程"）；T3 Non-Goals（"多模态输出生成" —— 输入在范围内，输出不在）。

### 6. Vector Database / RAG 基础设施

**描述。** 一个 embedding 索引和 ANN（近似最近邻）存储，支撑语义记忆检索，取代或补充 T3 §4 中基于关键字加元数据的 SQL 检索。

**触发条件。** T3 的 `Memory Backends` 扩展点（T5 MAY EP）已实现，并且某个插件作者（或项目本身）有一个具体的检索器需要在 `LIKE` 型 SQL 检索可衡量地不够用的规模上进行语义搜索。T3 ADR-3 是为消费级语料规模有意选择 SQL 检索的；触发条件是语料已超出该规模的证据。

**前置依赖。** T3 `memories` 表发布。T5 Memory Backends EP 接通。一项关于 vector store 是位于核心内（违反 T3 Non-Goals，需要一份取代性 RFC）还是仅位于 Memory Backends EP 背后（T3 背书的路径，无核心变更）的决策。

**粗略工作量。** 若在核心内为大型（embedding 模型依赖、ANN 库、重索引流水线、schema 迁移）；若仅在 Memory Backends EP 背后为中小型（一个插件自带其 vector store，核心不动）。

**来源。** T3 Non-Goals（"Vector database / RAG 基础设施"）；T3 ADR-3。

### 7. 插件开发 CLI / 脚手架

**描述。** 一个命令行工具，脚手架生成新的插件目录（`plugin.json`、能力子目录、一个起步 Tool 或 Skill），针对清单 schema 跑本地校验，并提供 dev 模式加载器。

**触发条件。** 社区反馈表明手工的"建目录 + 写 plugin.json"工作流是摩擦点。触发条件是可观察的：插件作者抱怨，或"读完插件文档"到"发布第一个插件"之间可衡量的流失。

**前置依赖。** T4 清单 schema 冻结（以便脚手架生成有效输出）。T5 扩展点契约稳定（以便脚手架的起步代码能编译到真实接口）。本地 dev 加载器是一项运行时便利，可以搭迁移路径中 X.3 清单加载阶段的便车。

**粗略工作量。** 中型。脚手架是一个 Yeoman 风格生成器加接到 CLI 的 schema 校验器；困难的部分是让它与 schema 演进保持同步，而不是初版构建。

**来源。** 没有任何 RFC 显式把它列为 Non-Goal，但由 T4/T5 中没有任何工具交付物所隐含。列在此处是为了不被遗忘。

### 8. Marketplace 支付 / 账户

**描述。** 付费插件、收入分成、用于购买和归属的用户账户，以及相关的金融基础设施。

**触发条件。** 项目作出的**商业化决策**。这是商业触发条件，不是工程触发条件。任何协议稳定性或用户需求都不能在没有明确变现决策的情况下启动它。

**前置依赖。** 插件 marketplace（条目 1）发布。插件签名（条目 2）发布 —— 没有签名的付费插件是明显的欺诈面。一个用户账户系统，本项目目前没有（2026-06-20 文档有意选择单用户加 token 认证）。

**粗略工作量。** 超大型。支付、账户和收入分成都带有让工程相形见绌的法律、合规和运营负担。

**来源。** T4 Non-Goals（"Marketplace / registry / 支付 / 账户系统"）；T6 Non-Goals。

### 9. 完整 Artifact 子系统

**描述。** 决策 B7 推迟的完整 Artifact 数据模型：版本管理（历史、diff、恢复）、导出格式（下载为 PNG/SVG/PDF/HTML）、多 artifact 链接（一个 artifact 引用或内嵌其他 artifact），以及用于 artifact 持久化的 SQLite schema。

**触发条件。** 按决策 B7，最小 Renderer 协议（T5 §4，本轮发布）必须已在生产中使用，其局限必须已被感受到。触发条件是：用户在生产 artifact，想跨回合修订它们，却无能为力 —— 此时完整子系统由真实摩擦而非功能完整性焦虑所证明。

**前置依赖。** T5 Artifact Renderer 协议（iframe + CSP 沙箱 + postMessage 通道）已发布并在使用。T2 的 Run 生命周期（以便 artifact 变更可绑定到 Run 步骤）。一项关于 artifact 是 per-session、per-user 还是 global 的决策 —— B7 把它留作开放。

**粗略工作量。** 大型。仅版本管理就是一份 schema、一个 diff 算法和一套恢复 UX。导出格式按格式倍增。多 artifact 链接是图模型。每项都是独立的子工作流。

**来源。** 决策 B7（"Artifact 子系统承诺" —— 本轮最小 Renderer 协议，完整模型推迟）；T5 Non-Goals（"完整 Artifact 数据模型"）。

### 10. 审计日志存储后端

**描述。** 一个用于 T6 `plugin.audit-log.schema.json` 定义的审计日志记录的持久存储 —— 一张 SQLite 表、一个 append-only 文件，或一个远程 sink。

**触发条件。** T6 的权限强制执行（迁移路径的 Phase X.6）正在落地，审计事件正在发出但只进结构化日志。触发条件是首次出于合规、调试或事后复盘目的而查询审计历史的需要。

**前置依赖。** T6 审计日志 schema 发布。T6 运行时权限检查接通（Phase X.6）。一项存储决策（SQLite 表是领先候选，与单数据库约定一致）。

**粗略工作量。** 中小型。schema 已经定义；这只是一张表的迁移加上既有 flat 风格的一个 repo 模块。

**来源。** T6 Non-Goals（"实现审计日志存储"）；T6 开放问题 2。

### 11. v2 实现规范差距（四项 HIGH 偏差收敛）

**描述。** Agent Loop v2 / Context v2 的首轮实现（implement-agent-loop-context-v2 工作波，19 commits，2026-08-15 终验通过）与 RFC 规范存在四项 HIGH 级偏差，均经终验 F1 审计确认、用户裁决"接受并记档"：（1）T2 §2 的有界并发池（`maxConcurrentTools` 钳制、每调用子信号 `AbortSignal.any`、`ToolCallOutcome` 四态失败聚合）未实现，保留 v1 的无界 `Promise.all`；（2）T2 §3 的 Extended Thinking 应以 `delta` 上可选 `kind` 字段暴露（ADR-003 明确否决新事件类型），实际实现为独立的第 12 种 `reasoning` SSE 事件（additive、向后兼容，但违反 RFC 合规条款 292）；（3）T3 §4 的记忆应为 `user_id` 作用域、跨会话（kind/content/entities/confidence 结构），实际实现为 `session_id` 作用域的 key-value 存储——不具备跨会话召回能力；（4）T3 §7 的 `RunContext` 应为六字段（messages/tools/cacheControl/budget/status/meta），实际为三字段（messages/budget/degraded）。

**触发条件。** 以下任一信号出现时迁移对应子项（四项相互独立，可逐项收敛，不要求捆绑）：(a) 并行工具调用在真实负载下出现可见的停滞或资源争用，需要并发钳制；(b) 有严格校验"SSE 事件集恰为 11 种"的第三方客户端集成需要 wire 格式收敛；(c) 出现真实的跨会话个性化需求（"记住用户偏好"类功能立项——session_id 作用域无法满足，需先重构为 user 维度）；(d) 某个子系统（如 Prompt Caching 的 adapter 层消费方）需要消费 `RunContext` 的 tools/cacheControl/status 字段。

**前置依赖。** 无硬前置。但每项需自带兼容策略：(1)、(4) 为纯服务端扩展，可直接补齐；(3) 涉及 `memories` 表 schema 迁移（列结构与主键变更）及存量数据迁移决策；(2) 涉及 wire 协议变更——`delta.kind` 与 `reasoning` 事件的并集过渡期或客户端强制更新，二者择一，需在迁移 RFC 中明确。

**粗略工作量。** (1)、(4) 中小型；(2) 中型（协议迁移 + 弃用期）；(3) 中型（schema 迁移 + 数据迁移决策）。合计约为一个小型工作波。

**来源。** T2 §2/§3、T3 §4/§7 规范条款 vs 首轮实现的 F1 终验审计（REJECT 判决，4 项 HIGH）；用户裁决 A（接受并记档，2026-08-15）。

## 反例

### 反例：在没有触发条件的情况下启动一个被推迟的条目

上面每个条目都有触发条件，正是因为在信号之前启动"有趣"工作的诱惑很强。一个在插件协议稳定之前启动 marketplace，或在真实工作流需要之前启动多 agent 编排的团队，要承担协议在它底下变化时的返工成本 —— 或更糟，为了规避返工而过早冻结协议。触发条件就是要被尊重的。如果某个触发条件触发，条目就进入规划待办；如果未触发，条目就留在这里。

### 反例：把多个被推迟的条目捆绑进一份 mega-RFC

把"marketplace + 签名 + 支付"作为一份协调 RFC 落地以避免集成摩擦，这很诱人。这是一种反例。每个条目都有自己的触发条件、自己的工作量特征和自己的依赖；捆绑它们会耦合它们的时间表和审查负担。v2 RFC 集（T2-T6）本身就被有意拆分，以便每份都能独立审查，同样的原则适用于未来工作。一个条目在它自己的触发条件触发时启动，而不是在邻近条目的触发条件触发时。

## 架构决策记录

### 决策 (ADR-1：触发条件是信号，不是时间表)

**背景。** 一份未来工作清单可以是日期驱动（"2026 Q3：marketplace"），也可以是信号驱动（"当协议稳定性被证明时：marketplace"）。

**选项。** (a) 日期驱动：给每个条目分配一个目标季度。(b) 信号驱动：给每个条目分配一个可观察的触发条件。(c) 混合：一些用日期，另一些用信号。

**决策。** (b) 信号驱动。本文件中的每个条目都有以可观察信号（协议稳定、用户需求、依赖落地、商业决策）表达的触发条件，而非日历日期。

**理由。** 本项目是自托管、面向单用户的；不存在让日期有意义的商业发布节奏。信号追踪现实：一个条目在证明它的条件出现时启动，而不是日历说该启动时。这也让本文件耐用 —— 它不会像日期驱动的路线图那样过时。

**备选。** (a) 需要本项目不具备的规划流程，并会制造虚假紧迫感。(c) 不带来任何收益地引入不一致。

## 迁移

本文件中没有任何条目属于当前 RFC 已承诺的范围。它们被列在此处正是因为 v2 浪潮（T2-T6）拒绝规范它们。一个条目从本文件迁移到活动设计，只在它陈述的触发条件触发时 —— 不提前，也不按时间表。

被推迟条目的迁移路径是统一的，且有意沉重，以防止待办条目在未经审查的情况下溜进实现：

1. **触发条件触发。** 条目 `Trigger condition` 字段记录的可观察信号被明显满足（协议稳定性被证明、用户需求被衡量、依赖落地、商业决策作出）。
2. **撰写一份新的独立 RFC。** 条目离开本文件，成为它自己的 RFC，范围限定为一个条目或一个紧密耦合的家族。把多个条目捆绑成一份 mega-RFC 是反例（见上）。
3. **该 RFC 走与 T2-T6 相同的审查和批准流程** —— 包括 Non-Goals、conformance 条款和适用的 ADR。
4. **只有在此之后实现才开始**，并对照 `docs/rfc/migration-and-prior-art.md` 中尊重依赖的迁移路径（phases X.1-X.6）排序。

**顺序依赖。** 若干条目带有硬前置依赖，约束了它们可以迁移的顺序，与它们自己的触发条件何时触发无关：

- 插件签名（条目 2）**必须**（MUST）在 marketplace（条目 1）之前迁移 —— 没有签名的 marketplace 是未缓解的供应链攻击面。
- Memory Backends 扩展点（T5 MAY，在 phase X.5 落地）**必须**（MUST）在某个 vector DB / RAG 条目（条目 6）能在其背后迁移之前接通。
- marketplace（条目 1）**必须**（MUST）在 marketplace 支付 / 账户（条目 8）之前落地，因为支付以分发界面为前提。
- Artifact Renderer 协议（T5 §4，phase X.5）**必须**（MUST）在完整 Artifact 子系统（条目 9）迁移之前处于生产使用 —— B7 推迟它正是为了让最小协议的局限先被感受到。

**无自动迁移工具。** 与本计划不提供自动迁移工具的 Non-Goal 一致，每次迁移都是人工撰写的 RFC。本文件是规划工件，不是工具可以排干的队列。

## 开放问题

1. **信号衡量。** 像"用户需求"或"协议稳定"这样的触发条件具体如何衡量？本文件陈述信号；它不定义检测它们的埋点。后续可能定义一个轻量级遥测界面。
2. **重新纳入流程。** 当一个触发条件触发时，把条目从本文件移到活动规划待办的流程是什么？可能是一份取代相关 Non-Goal 的新 RFC，但工作流在此未形式化。
3. **条目优先级。** 如果两个触发条件同时触发（例如 marketplace 需求和签名需求，它们是耦合的），哪个先走？本文件把它们当作独立的；实践中签名阻塞 marketplace（条目 2 是条目 1 的前置依赖）。
4. **条目退役。** 如果一个条目的触发条件永不触发，该条目何时从本文件移除？此处没有 sunset 机制；隐含需要定期审查，但未排期。
